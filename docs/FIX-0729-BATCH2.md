## 逐条改动

### 1. 两个进度接口解耦（根因 1）

原来 `Promise.allSettled` 把索引和预载绑在一起等，两个都回来才赋值。预载接口是纯内存
读取，被索引接口拖着。现在拆成 `loadIndex()` / `loadPreload()` 各发各的、各自渲染，
各自在 `finally` 里调 `syncPoll()` 决定轮询开关。

两侧各加了一个在途标记（`idxInflight` / `preInflight`）：接口偶尔慢过一个轮询间隔时，
请求不会越堆越多。原来的 `setInterval(async fn)` 没有这道闸。

### 2. 索引条数改后台数（根因 2）

`index.go` 的 `Progress()` 第一件事是 `refreshCount()` → `SELECT COUNT(*) FROM files`，
跑在请求线程里，和预载、媒体库查询抢那 4 条 SQLite 连接，最坏排到 `busy_timeout` 的 5 秒。

现在起 goroutine 去数，本次先返回上一次的数字，下一次读进度（轮询 1.5 秒一轮）就是新的。
UI 上的滞后至多一格轮询，看不出来。

两个不变量：

- `counting` 标记防止 1.5 秒一次的轮询起出一串重复的 COUNT。
- `countGen` 代际号在 `Rebuild()` 与 `Clear()` 里递增。这两处会给出权威条数，此时在途的
  后台计数数的是改动之前的表，回填就会把正确数字覆盖成旧的。写回前比对代际，不符就丢弃。

实测（158 行的库）：写操作之后立刻读进度返回旧的 1，下一次读返回 2。

### 3. 轮询在首个响应之前就开着（根因 4）

原来定时器装在 `await` 之后，首个响应回来前一次都不轮询。现在 `onMounted` 里先
`startPoll()` 再发第一次请求；首个响应到了 `syncPoll()` 自会按状态收摊。

`syncPoll()` 的 busy 判据里加了「首个响应还没到齐」——那会儿还不知道后台是不是正忙，
不能停。

### 4. 百分比一位小数 + 本轮已跑（根因 5）

单件最坏两三分钟、并发才 2，总数上千时整数百分比几十分钟才跳一格。

- 百分比保留一位小数（`Math.round(x * 1000) / 10`）。
- 「已处理 N / M 项」后面接「本轮已跑 X」。一分钟内按秒走，跟着 1.5 秒的轮询一跳一跳，
  这是最直接的「没死」信号。

时刻来自后端新加的 `Progress.StartedAt`：每次 `start()` 都重记，包括推迟后「继续」的那次
——沿用旧时刻的话，推迟一天再继续，卡片会说这一轮跑了 24 小时。

### 5. 清点阶段不再显示恒定 0%（接第 1 批的 `Phase`）

第 1 批给 `preload.Progress` 加了 `Phase`（`counting` / `running`），但它的消费方在
`AdminIndex.vue`，属于本批的文件。现在：清点阶段走不确定态进度条，并且不显示
「已处理 0 / 0 项」（那会儿总数还没算出来，写出来是误导），只留「正在预载：清点已缓存的
部分…」和「本轮已跑 X 秒」。
