# 快进卡顿排查与首块流式直通（2026-07-30，v2.2.1）

## 现象

Google Drive 上的 mp4，**有的快进一拖就卡几十秒，有的秒开**。同一台服务器、同一个盘、
同样是直连 mp4，与码率和文件大小都不相关——卡的那个 910MB，不卡的反而 1.07GB。

## 诊断（全部有实测支撑）

**链路先澄清**：Google Drive 直链必须带 `Authorization: Bearer`，302 会丢头，所以
`handler_raw.go` 对它一律强制中转，**与挂载的「代理模式」开关无关**。实际链路是
`浏览器 → /api/raw → stream.Serve 并发分块 → googleapis`。

**1. 卡的那个文件 moov 在文件尾。** 拉文件头 64 字节看 box 结构：

```
offset 0            ftyp   32 字节
offset 32           free    8 字节
offset 40           mdat   953,979,606 字节
offset 953,979,646  moov   ≈379KB        ← 索引在最后，不是 faststart
```

Chrome 必须先拿到 moov 才能播，于是跳着发几十条零碎 Range 请求去捞索引；每次快进还要
再翻一遍索引表定位关键帧，所以**快进比起播更难受**。

对照组（不卡的那个）首个请求是 `bytes=0-`，一条拿到 3.6MB 连数据带索引，**全程 2 条请求**。
卡的那个首请求是 `bytes=32768-`，几十条，每条只实收 16~267KB。

**2. 每条请求都要先付 0.86 秒。** 服务器上直接 curl 同一区间：

```
速度 1,126,027 B/s | 首字节 0.863573s | 实收 10,000,000 字节
```

服务端→Google Drive 这一段是健康的（10MB 一气呵成、零断流、`[stream]` 一条错都没报）。
那 0.86 秒的构成：

```
0.863 秒 = 固定开销（取直链 + 建连 + GDrive 寻址）+ 512KB 传输（524288 ÷ 1126027 ≈ 0.466 秒）
        ⇒ 固定开销 ≈ 0.398 秒
```

**3. 病灶：`accel.go` 的首块必须下满才吐第一个字节。** 浏览器只要 32KB，服务端却要先把
512KB 凑齐（`io.ReadFull`）。单次大请求付一次可忽略；几十条索引探测请求每条都付，
叠起来就是 DevTools 上那 35 秒。而浏览器发的是 `bytes=32768-` 这种开放式 Range，
服务端按剩余 910MB 排分块计划，无从知道对方只想要 32KB。

**4. 短传是结果不是原因。** 承诺 `Content-Length: 28049408` 实发 425984 字节
（= 13 × 32768，即 `io.Copy` 的 13 次写），浏览器只能用同一终点从断点重发，一秒一轮。

## 改动

`internal/stream/head.go`（新）
- 块 0 改流式直通：上游响应一到就转发，不等整块下满。
- 只有块 0 走这条路——块 1 及之后本就在并发预取，读到时已在内存里，没有等待可省，
  流式化它们只会破坏「按序拼接」的前提。
- 流一旦开始就无法整体重发，故中断后**带偏移续拉**（`headResumes = 4`）；耗尽即让响应
  短传，由客户端按 HTTP 语义自行续传。

`internal/stream/accel.go`
- 抽出 `openRange`（只打开不读）与 `openWithRetry`（泛型重试驱动）。首块流式与整块下载
  共用同一套状态码判定和「换链 / 限流等待 / 退避」策略，避免两处漂移。
- head 占一个并发名额：`threads≥2` 时总在途连接数不变；`threads=1` 从 1 条变 2 条
  （head 流 + 1 个 worker）。不留这个 worker 的话块 1 之后无人下载，读端会永远等下去。

## 测试

`internal/stream/head_test.go`：`TestHeadStreamsBeforeChunkComplete`（块 0 没下满就必须
吐字节）、`TestHeadResumeAfterBreak`（吐一半被掐要从断点补齐）、`TestHeadResumeGivesUp`、
`TestHeadRelinkOn403`、`TestHeadCloseConcurrentWithRead`、`TestHeadOnlyChunk`。

前两条验过能红：把 head 摘掉退回 `io.ReadFull`，分别报 `块 0 尚未下满就该吐字节` 与
`实际请求起点: [131072 0 0]`（整块重发而非断点续拉）。

`TestSingleThread` 的断言同步修正——「请求起点严格递增」在 head 惰性打开后不再成立
（块 0 何时发出取决于读端何时开始读，与 worker 启动是两条独立时间线），改为只对
块 1 及之后断言递增。

## 天花板与下一步

这层拿走的是每请求约 **0.466 秒**的等块时间，**留下约 0.398 秒固定开销**。它治「每条请求
慢」，治不了「请求条数多」——后者的根源是 moov 在文件尾。

判据（部署后量一次，拉 1 字节即纯固定开销，不掺传输）：

```bash
curl -o /dev/null -s -w "首字节 %{time_starttransfer}\n" -r <某位置>-<同一位置> '<raw URL>'
```

- ≈0.4 秒 → 固定开销是大头，**须上第二层**
- ≈0.1 秒 → 0.86 秒里绝大部分是等 512KB，这层基本够了

第二层备选（未做）：
1. **服务端缓存 moov** — 首次播放把文件尾那段索引拉下来常驻，后续索引请求本地命中。
   文件不用动，对用户透明。
2. **文件转 faststart** — 从源头把几十条请求变成 2 条，但要重新封装。
