# 转存链路：提速与限流可靠性（2026-07-25）

起因是把 3.71TB 从 OneDrive 迁到 Google Drive，暴露出两类问题：断点续传的探测慢得离谱，
以及一撞限流整个文件夹任务就失败。三块改动彼此独立，按发现顺序记在下面。

## 一、断点续传探测：每文件一次 Stat → 每目录一次 List

**根因不在 Stat 本身，在调用次数。** `googledrive`/`pikpak` 的 `lookup` 是递归解析 + TTL 缓存，
但**只缓存「找得到」的路径**：文件不存在时直接返回 `ErrNotFound`，不留任何记录。于是首次复制
（目标目录空）或目录里缺文件时，**每个文件的 `Stat` 都会把目标目录整个 `listAll` 一遍**，
大目录还要分页。500 个文件 = 500 轮全目录列举。OneDrive 好一些（按路径精确查单个 item），
但也是每文件一次 Graph 请求。

**改法**（`internal/fs/transfer.go`）：复制开始前，对**有文件要落地的**目标目录各 `List` 一次，
建 `路径 → 大小` 的内存快照，文件级判断查内存。请求数从「文件数」降到「目录数」。

三个保守点：

- **单文件转存不预扫**——只为一个文件去列一个可能很大的目标目录是净亏，仍走一次 `Stat`
- **某目录列不出来**（无权限等）只让那个目录退回逐文件 `Stat`，只慢不错，不会漏跳或误跳
- 快照在起 goroutine 前建好，只读，并发安全

顺带：GDrive 的 `List` 会把每个子项写进驱动缓存，预扫描等于把缓存一次填满。

验证 `TestTransferResumeScansOncePerDir`：12 个文件重跑，断言 **Stat 0 次、List 1 次**。
反向验证（临时关掉预扫描）报「实际 12 次」。另有 `TestTransferSingleFileSkipsPrescan`
守住单文件不预扫，防止以后被「顺手统一」掉。

## 二、路径解析加负缓存

上面那条只治了转存路径，`lookup` 本身仍然不记「这个路径不存在」，其他调 `Stat`/`Link`
的地方照吃放大效应。给 `cacheEntry` 加 `missing` 标记，列举完父目录仍没找到就写负缓存。

**安全性是逐条核对过的，不是假设。** 负缓存最怕盖住刚写入的文件（上传完却被判成不存在，
播放和续传全错）。两个驱动的每一条写路径：

- GoogleDrive：`Put` / `MakeDir` / `Rename` / `Remove` / `Move` / `Copy` 成功后全部 `cacheClear()`
- PikPak：`MakeDir` / `Rename` / `Remove` / `moveOrCopy` 全部 `cacheClear()`；它没有 `Put`（不支持上传）

`cacheClear` 是整表清空，负缓存跟着一起没。外部改动（网页端新建）与正缓存一样受 TTL 约束，
没有引入新的陈旧窗口。

验证：两个驱动各一个 `TestLookupNegativeCache`，断言重复查不存在的路径不再发请求、
**负缓存不波及同目录下真实存在的文件**、`cacheClear` 后重新发起列举。

## 三、限流退避与错误定位

**原来是「只重试 1 次、等待钳到 5 秒」**，而项目自己在 `stream/accel.go` 的注释里就写着
「OneDrive/SharePoint 的 Retry-After 常达数十秒」——服务端让你等 30 秒，代码 5 秒就冲上去，
必然再撞。撞满就整任务失败。

**更要命的是上传路径原本完全没有退避**：它们绕过 `req` 直接 `httpClient.Do`，而那正是
请求量最大的地方。

改法：

| 路径 | 处理 |
|---|---|
| `req` / `reqHeader`（元数据） | 按 `util.ThrottleWait` 退避 4 次 |
| `putChunk`（两端，大文件分块） | 就地按 `Retry-After` 退避——分块在内存，重发绝对安全 |
| `doUpload` / `putSmall`（小文件） | **仅当 body 能回绕（`io.Seeker`）才就地重试** |
| `copyOne`（文件级重试） | 重试之间退避，限流等更久 |

`util.ThrottleWait`：有 `Retry-After` 就听服务端的，否则 2/4/8/16 秒递增，统一钳进 **[1s, 60s]**。

小文件那条是**刻意保守**：转存时 body 是源端网络流，读过就没了，就地重发只会传出半个文件。
这种情况原样返回，交给上层重来整个文件。GDrive 的 multipart 分支已整个在内存，改传
`bytes.Reader` 让它能就地重试。

分块循环的外层用 500ms 级退避而非秒级：限流已由 `putChunk` 内部按 `Retry-After` 处理，
外层只管网络抖动，两者节奏不同。

### 错误能定位了

新增 `util.Contextf`（附上下文，内层仍翻译）与 `util.Messagef`（调用方已写好人话，不再翻译内层），
`Humanize` 都认得。失败信息从光秃秃一句「请求过于频繁」变成：

```
复制 相册/2024/a.mp4 失败（写入目标，已重试 2 次）：请求过于频繁，请稍后重试。
```

归因**按实际读写行为判定**：上传中途失败时，若 `countingReader` 报过读取错误，锅算在源端
而不是目标端（`transfer.go` 的 `stage` 逻辑）。反向验证去掉判断后测试立刻报「写入目标」。

### 每日额度与瞬时限流分不出来，用行为分流

**实测确认（官方文档没有记载）：Google Drive 每天 750GB 上传额度用尽时，返回的是
403 `userRateLimitExceeded`——与并发过高导致的瞬时速率限流完全同一个码。**
官方 handle-errors 页面只定义了 `storageQuotaExceeded`（总容量）和 `dailyLimitExceeded`
（API 调用次数），都不是每日上传字节量。

错误码分不出来，但**行为**能分：退避 4 轮还是不通，就不是瞬时抖动。所以 `copyOne` 在
限流耗尽时用 `Messagef` 换一套说法，不再劝「稍后重试」：

```
复制 … 失败（写入目标）：反复被限流。请调低「文件夹内并发」后重试；
若持续如此，可能是云盘每日上传额度已用尽，明天再继续。已传完的文件不会重传。
```

## 运维要点

- **两个并发设置是相乘的**：「复制任务线程」（同时几个任务）×「文件夹内并发」（每任务内几个文件）
  = 实际同时在传的文件数。曾设 25 + 两个文件夹同时复制 = 50 路，稳定撞瞬时限流；降到 10 解决。
- **每日 750GB 与并发无关**，传得快只是更早撞到，总量一样。3.71TB 至少要 5 天，硬约束。
- **撞额度后当天无解**，调并发、多等都没用。普遍说法是按太平洋时间午夜重置（北京时间下午 3 点前后，
  夏令时），也有说滚动 24 小时——未实测确认。断点续传保证明天重试不浪费额度。
- **原始错误在服务日志里**：`task.go` 失败时 `log.Printf` 原始 `err`，含云盘的 reason 和英文消息；
  界面上被 `Humanize` 换成了人话。排查限流类问题一律看日志。

## 刻意没做

- **OneDrive 没加路径缓存**：它的 `Stat` 是按路径精确查单个 item，不是「列整个目录再找」，
  没有放大效应；转存路径已被预扫描覆盖。单独给它做一套缓存收益不明显。
- **503 没按限流处理**：本轮只覆盖 429 与 403 限流码，与既有 `isRateLimited` 判定保持一致。
  要加得在所有路径统一加，是另一个决定。
- **每日额度没有独立错误码**：见上，只能靠「退避耗尽」这一行为分流文案。

## 测试

`util` 四个新测试（退避时长表、限流判定与文案同源、`Contextf`/`Messagef` 穿透 `Humanize`）、
两个驱动的负缓存测试、`fs` 的预扫描请求计数 / 退避策略表 / 错误归因与限流文案断言。

给 `FS` 加了测试可替换的退避钩子 `retryBackoff`（生产为 nil 走默认策略），重试类测试不再
白等真实 sleep——`internal/fs` 从 5.9s 回到 1.9s。策略本身由 `TestCopyRetryWait` 单独盯着。
